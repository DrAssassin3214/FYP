Final-year project · B.Tech Civil Engineering

Masonry Delay-Risk Decision Support

A tool that takes what is known about one brick or block masonry activity, runs it through a fixed simulation, and says which response is preferred and why. Every figure on screen traces to an input you gave or a paper it cites.

One activity: brick / blockwork masonry, India · written 28 Sep 2026

Update. The interface and service were later reduced to risk identification, the risk register and the risk matrix. The simulation, cost and decision steps described in Figure 1 (steps 4 to 6) are no longer part of the app. The rules, the guarded AI layer, the evidence corpus and the literature harvest below are unchanged.

What it does

You describe the activity (quantity, crews, deadline), the risks that could delay it (each with a probability, a delay range and a cost, and where each number came from), and the mitigations you could pay for. The tool simulates the activity many thousands of times, reports how late it is likely to finish and what that costs, re-runs it for each mitigation option, and states which option is preferred under a rule you chose.

It will not

  • Invent a number. AI may suggest risks and cite papers. Probabilities, delays and costs come from you, from site records, or from a cited source.
  • Call anything optimal. It reports the option preferred under the stated criterion, among the options actually evaluated.

It also does not

  • Fit a new productivity equation. Productivity comes from published models, or a range you enter, with warnings when you go outside a model's validity range.
  • Train on the papers. The literature is a searchable evidence store the AI must cite from. No model is fitted to it.

How a run works

  1. Inputs

    Screens 1 to 8 of the interface collect them. Each number that matters carries a Source label (below).

  2. Case check

    Nothing runs until every number has a Source and is in range. Problems come back as plain messages that name the field, never as a silent default.

  3. Prepare

    Baseline duration T0 comes from published models, converted to m2/day per crew and pooled by sample size when several apply, or from your own range. The rule engine reads site facts and warns about elevated risks missing from the register. India labour norms (IS 7272, CPWD) are a citable reference and are never applied automatically.

  4. Simulate

    Each run starts at T0 and adds, for every risk, a delay drawn from its distribution if a Bernoulli draw with probability p says the risk occurs. Correlated risks and productivity spread are optional. The seed is fixed and shared by every option.

  5. Analyse and decide

    Schedule percentiles with intervals, the chance of missing the deadline, expected cost with liquidated damages, and which risks drive the delay. Each option is re-simulated with the same random numbers. Options that break a stated limit are excluded, and the admissible option that scores best on the chosen criterion (default: lowest total expected cost) is reported as preferred.

  6. Outputs

    Twelve screens, a written report.md, and an audit.json holding the input hash, seed, run count and assumption register, so any figure can be reproduced.

Simulated expected cost and the sum of event-level EMV can differ. Liquidated damages are non-linear in delay, so the average of the cost is not the cost of the average delay. The Cost screen shows both and says why.

Every number has a Source

This rule shapes the whole tool. A value cannot enter a run without one of these labels, and the report lists everything labelled Assumption so a reader can see what is not evidence.

BadgeMeaningTypical use here
LITLiteratureA value stated in a cited paper or standard
HISHistoricalSite or company records
USRUser inputQuantities, deadline, crew sizes
EXPExpert judgmentProbabilities and delay ranges from an engineer
DERDerivedComputed from other labelled inputs
ASMAssumptionPlaceholders, always called out

Where AI fits

With no key configured the tool runs fully offline: suggestions become a plain search of the evidence store and the explanation is the deterministic text. The key is saved in the per-user application-data folder, outside the project, so zipping the project for submission does not carry it.

Run it

python -m gui                                  # local interface at http://127.0.0.1:8765/
python -m app.cli template > my_case.json      # blank case to fill in
python -m app.cli run my_case.json --out out/  # report.md + audit.json
python -m pytest                               # full test suite
The input format is documented in docs/case_schema.md, and each screen is described in gui/README_GUI.md.
